# 언제충전 (eonje) — 요구사항

2026.10.09 초안. 설계는 [design.md](./design.md).
이 문서는 **무엇을 만들고 무엇을 만들지 않는지, 언제 됐다고 보는지**를 정한다. 설계와 달리 자주 바뀌지 않아야 한다.

## 1. 문제 정의

전기차 차주가 겪는 문제는 충전기 위치를 모르는 것이 아니라 **가 보면 차 있는 것**이다. 공식 API와 기존 앱(EV Infra, 모두의충전, ChargEV 등)은 충전기의 현재 상태와 빈자리 알림을 제공하지만, 과거 이력을 쌓지 않아 "보통 언제 비는가", "이 충전기는 며칠째 고장인가"에 답하지 못한다.

이 서비스는 충전기 상태를 계속 수집해 이력 기반 정보를 제공한다. 차별점은 이력이고, 알림 같은 부가 기능도 이력 위에서만 만든다 (예: 단순 빈자리 알림이 아니라 "보통 이 시간대에 비니 그때 알려줌").

## 2. 사용자

- 주 사용자: 전기차 차주. 자주 가는 충전소(집·회사·단골 경로)가 몇 곳 있고, 그곳이 언제 비는지 알고 싶다
- 부 사용자: 충전 인프라에 관심 있는 사람(운영기관·지자체·연구·기사). 지역·시설 유형 단위 통계를 본다
- 운영자(본인): 수집이 정상인지, 데이터 품질이 어떤지 본다

## 3. 플랫폼 단계

| 단계 | 플랫폼 | 비고 |
|---|---|---|
| 1 | 반응형 웹 | 데스크톱·모바일 브라우저. 계정 없음 |
| 2 | 웹 + 계정 | 관심 충전소 저장. 모바일 확장의 전제 |
| 3 | 모바일 앱 | iOS·Android. 웹과 같은 API 사용. 푸시 알림은 이 단계부터 |

모바일 확장을 전제로 하는 설계 제약:
- **API 우선.** 웹은 API의 첫 클라이언트일 뿐이고, 모바일은 두 번째 클라이언트다. 웹 프론트에만 있는 로직은 없어야 한다 (집계·판단은 전부 서버)
- API 응답은 버전을 가진다 (`/v1/`). 모바일은 업데이트가 느리므로 하위 호환을 깨지 않는다
- 계정·인증은 2단계에서 도입하되, 1단계 API도 인증 헤더가 들어갈 자리를 비워 둔다
- 지도·차트 같은 표현 계층은 플랫폼별로 다시 만들어도 되지만, 그 입력 데이터 형식(히트맵 배열, 충전소 목록)은 공통이다

## 4. 기능 요구 (FR)

우선순위: P1 1단계 필수 / P2 1단계 후반 / P3 2·3단계.

화면은 셋이다: **탐색**(지도/목록) → **충전소 상세** → (충전기 상세는 상세 안의 펼침). 통계·비정상 목록·운영은 별도 화면.

### 4.1 충전소 탐색

| ID | 요구 | 수용 기준 | 우선 |
|---|---|---|---|
| FR-01 | 사용자는 지도 또는 목록에서 충전소를 찾는다 | 지역(시군구)·시설 유형·충전 타입(급속/완속)·출력으로 필터. 지도 범위 안 충전소 표시 | P1 |

| ID | 요구 | 수용 기준 | 우선 |

| FR-04 | 사용자는 충전소 상세 화면에서 기본 정보를 본다 | 이름·주소·시설 유형·운영기관·이용시간·주차료·이용제한·충전기 수(급속/완속 분리)·출력 범위 | P1 |
| FR-05 | 상세 화면 상단에 요약 지표가 표시된다 | ① 지금 시간대 평균 점유율(FR-10 기준) ② 지금 빈 충전기 있을 확률(FR-40, 없으면 숨김) ③ 평균 세션 길이(FR-14) ④ 비정상 충전기 수(FR-20) ⑤ 집계 기간과 관측 수(신뢰도). 각 지표는 데이터 부족 시 값 대신 "부족" | P1 |
| FR-06 | 상세 화면에 요일×시간대 히트맵이 표시된다 | FR-10·11·13 적용. 현재 요일·시간 칸 강조 | P1 |
| FR-07 | 상세 화면에 "비는 시간대" 요약이 표시된다 | 히트맵에서 요일별 점유율 최저 시간대 상위 3개를 문장·목록으로. 관측 부족 칸 제외 | P2 |
| FR-08 | 상세 화면에 충전기 목록이 표시된다 | 충전기별 타입·출력·마지막 관측 상태·마지막 관측 시각·비정상 지속 일수. 선택하면 FR-12 충전기 단위 패턴 펼침 | P1 |
| FR-09 | 상세 화면에 현재 상태는 참고 정보로만 표시된다 | 마지막 관측 시각을 반드시 함께 표시("N분 전 기준"). 실시간을 보장하지 않음을 명시 | P1 |

### 4.8 알림 (3단계)

알림은 10분 주기 수집으로는 성립하지 않는다 (최대 10분 지연). 아래 둘 중 하나가 전제다: 운영계정으로 한도 상향, 또는 `getChargerStatus`의 `statId` 필터로 **관심 충전소만 짧은 주기로 집중 폴링**. 집중 폴링은 호출 1회 = 충전소 1곳이라, 알림 요청이 들어온 충전소만 그 시간 동안 폴링하면 한도 안에서도 가능하다.

| ID | 요구 | 수용 기준 | 우선 |
|---|---|---|---|
| FR-60 | 사용자는 관심 충전소가 비면 알림을 받는다 | 사용자가 "지금부터 M분 동안" 요청 → 그 충전소만 1~2분 주기로 폴링 → 상태 3→2 전이 시 푸시. M 종료 시 폴링 중단. 알림 지연 2분 이내 | P3 |
| FR-61 | 알림은 패턴과 결합한다 | 요청 시점에 "보통 이 시간대는 X분 뒤에 빈다"를 함께 보여주고, 그 시각 전후로 폴링 밀도를 높인다 | P3 |
| FR-62 | 사용자는 비정상 충전기 복구 알림을 받는다 | 관심 충전소의 장기 비정상 충전기가 정상(2)으로 돌아오면 알림. 일 1회 수집으로 충분 | P3 |
| FR-63 | 알림 폴링은 예산 관리자를 거친다 | 집중 폴링 호출도 `api_call_log`에 기록되고, 한도 근접 시 신규 알림 요청을 거절한다 | P3 |

## 5. 비기능 요구 (NFR)

이 프로젝트에서는 비기능 요구가 본체다. 파이프라인 품질이 서비스 품질이다.

### 5.1 수집

| ID | 요구 | 기준 |
|---|---|---|
| NFR-01 | 호출 한도를 넘지 않는다 | 일 한도(설정값, 현재 1,000)의 95%를 넘기 전에 상태 수집을 자동으로 늦추거나 건너뛴다. 한도 초과 0회 |
| NFR-02 | 수집 지연 | 변경분 수집 주기(설정값, 현재 10분) 안에 관측이 적재된다 |
| NFR-03 | 수집 중단 복구 | 수집기가 죽었다 살아나면 자동 재개. 중단 구간은 결측으로 기록되고, 다음 전체 스냅샷에서 상태가 보정된다 |
| NFR-04 | 원본 보존 | API 응답은 가공 없이 영구 보존. 어떤 정제 결과도 원본에서 재생성 가능 |
| NFR-05 | 스키마 변화 내성 | 응답에 미지 필드·미지 코드가 와도 수집은 실패하지 않고 보존·보고한다 |
| NFR-06 | 수집 경로 분리 | 정기 수집(변경분·전체)과 알림용 집중 폴링은 같은 예산을 쓰되 서로의 스케줄을 막지 않는다 |

### 5.2 처리

| ID | 요구 | 기준 |
|---|---|---|
| NFR-10 | 멱등 | 같은 구간을 몇 번 재실행해도 결과 테이블이 같다 |
| NFR-11 | 결측의 명시 | 관측이 없는 구간은 "비어 있음"이 아니라 "모름"으로 다뤄진다. 점유율 분모에 들어가지 않는다 |
| NFR-12 | 세션 복원률 | 전체 스냅샷 기준으로 추정한 세션 중 변경분 수집에서 복원된 비율을 측정·공개. 목표는 데이터 쌓인 뒤 설정 |
| NFR-13 | 집계 신선도 | 집계 테이블은 마지막 관측 기준 1시간 이내 |

- 상시 빈자리 감시 알림 (모든 관심 충전소를 항상 폴링하는 방식 — 한도상 불가능하고 기존 앱 영역. 알림은 FR-60~63의 요청 기반·시간 제한 방식만)
- 결제·충전 시작·회원카드
- 길찾기·내비게이션
- 이용자 리뷰·사진
- 운영기관에 대한 고장 신고 대행
- 공식 API 외 소스 크롤링

## 7. 성공 기준

- 1단계: 서울 기준으로 관심 충전소 하나를 골라 "언제 비는지" 질문에 상세 화면 하나로 답할 수 있다. 수집이 한 달 이상 끊기지 않고 돌아간다
- 2단계: 본인 외 사용자가 관심 충전소를 저장해 쓴다
- 3단계: 같은 API로 모바일 앱이 동작하고, 요청 기반 빈자리 알림이 2분 이내 지연으로 온다

## 8. 미결

- 패턴 집계 기간 N주 기본값 (4주 vs 8주 — 데이터 쌓인 뒤 결정)
- 비정상 판정 임계 D일 기본값
- 소셜 로그인 제공자
- 모바일 기술 선택 (React Native / Flutter / PWA 선행 여부) — 3단계 진입 시 결정
- 알림 전제: 운영계정 전환 vs 집중 폴링만으로 충분한지 — 2단계 사용자 수 보고 결정
- `getChargerStatus`의 `statId` 필터가 `period` 없이 해당 충전소 전체 상태를 주는지 실측 필요 (집중 폴링의 전제)
- 공공누리 유형
